# Safeer Browser for Linux 1.0.107 · Safeer Control 2.1.63 · Safeer OS 0.4.65

## Security: commands between devices are signed with the device key and encrypted from device to device (Safeer Control 2.1.63)

Release 1.0.105 made every device decide for itself what each other device may reach on it. That decision, however, still rested on the device id which the hub writes into a message it routes. Measured on 7 October 2026 in a local test: an id that merely looks like the id of another device was given that device's access. And by construction a hub routes these messages unencrypted and writes the sender into them itself, so whoever hosts a hub could read the commands and answers it routes (file lists, what is playing, addresses and tokens of the file server) and name any sender.

Versions 1.0.106 / Safeer Control 2.1.62 / Safeer OS 0.4.64 were prepared and tagged but **not published**: a second independent review found the defects described below before publication. This release fixes them; it went through four more reviews before publication.

From this release two devices prove their keys to each other, and the device that holds the content decides by the key:

- **A protected session between two programs.** Each side signs its part of the handshake with the device key – the key that is already in your circle of trust – and the other side verifies it with the key from *its own* copy of the circle. The session key comes from a one-time ECDH exchange (P-256), so the device key only ever signs. Messages are encrypted with AES-256-GCM, each direction with its own key and a strictly increasing counter.
- **What travels protected:** commands (`control.command`), their answers (`control.result`), a page or a stream that opens by itself (`cast.url`), playback control (`cast.control`) and "continue on this device" (`handoff.request`). The hub forwards a signed handshake and encrypted pieces; it sees neither the command nor the answer. The address, the certificate fingerprint and the token of the file server arrive inside the protected answer.
- **Access is decided by the key.** For a protected message the computer looks up access by the id derived from the *verified key*, not by the id written into the message.
- **No way back to unprotected.** Once a device has proven its key to this computer, the computer no longer accepts these messages unprotected in that device's name – from anyone – and answers that device protected only. Neither an entry planted in the circle of trust under the device's id nor a hub that hides the device's capability in the device list switches this off. A program sets up protection with a device that announces it as soon as it appears in the device list, not only at the first command – also after its own restart, when it no longer has the old sessions.
- **An answer must come from the device that was asked.** An answer to a protected command is accepted only from the verified session of that device.
- **Every command is sent exactly once.** If the other device no longer knows the session, the command is not sent again: the "no session" notice is unsigned, so a hub could send it too and have an already executed command repeated. The sender is told at once; the next command uses a new session.
- **The sender learns what happened to a command – once.** A multi-part message counts as accepted only when the hub accepts its last part, and as rejected when the hub rejects any part. A command that waits for a handshake longer than 8 seconds is not sent late: the sender gets an error. For acknowledgements the program remembers only the type and id of a sent message, not its content.
- **Removing a device takes effect immediately.** A session is valid only while the device key is in your circle of trust.
- **An id that carries another device's name gets nothing.** An id derived from a key (`n-…`) under which the circle of trust holds a *different* key has no access at all – on the unprotected path too – and shares nothing that was stored for the real device.
- **Device ids and handshake fields have a strict form.** A device id is at most 128 visible ASCII characters; an id derived from a key carries only a program suffix of letters, digits, dot, underscore and hyphen; one-time keys, signatures and the other handshake fields are strict base64. This is checked before anything is signed or verified – an id with a line break or a space never enters a handshake.
- **One device cannot push out or overload the others.** At most 16 sessions per device (unconfirmed and superseded ones make room first); memory for multi-part messages is capped per device (8 MiB) and in total (32 MiB). At most 32 signatures with the device key per device per minute – counted separately for handshakes this computer starts and for answers to the other device's offers; a repeated offer triggers no signature, and after a failed handshake no new one is started with that device for three seconds. Messages waiting for a handshake may hold at most 4 MiB per device and 16 MiB in total. A device list sent by a hub starts at most 16 handshakes, at most 4 per device per minute, and only with devices whose key is in the circle.
- **A message with an unusual form does not reach the program.** A message id is a string of at most 128 characters or a number; anything else is dropped, also when it arrives on the protected path.
- **The permissions file is shared safely by the programs of this computer.** Safeer Control, Safeer OS and the browser write it under a file lock, from the state on disk, and check right before replacing it that no other program changed it in the meantime. If the file cannot be read, no device has access (previously the inherited rights applied) and the file is not overwritten.
- **Only the agreed message types travel protected.** A paired device cannot use the protected path to send what otherwise only a hub sends (the device list, the circle of trust, a pairing code).
- **Older devices keep working as before** until they are updated – and are only as protected as before. When a program without protection sends a command in the name of a device that has it, it receives the answer "The command did not arrive protected. Update Safeer on the device that sends it."

Both devices need this release for protection: Safeer Control 2.1.63 / Safeer Browser 1.0.107 on a computer, Safeer OS 0.5.65 on a TV, tablet or phone. Update all Safeer programs on one device together – they share the device key, and once one of them has proven it, updated devices refuse commands from an older program of the same device.

**Pre-release reviews.** Before release the protection code was reviewed six times, separately from development (internal reviews; not an external security audit). Every finding was first reproduced with a failing test and only then fixed. The fixes made after the sixth review were not reviewed a seventh time: they are covered by tests that failed first and by measurements before and after the fix.

1. *The first review* found two defects: (a) with a forged "no session" notice a hub made an already executed command run again – four times after three notices in the test (which is why commands are no longer re-sent); (b) an offer from another device that reused the session id of a handshake this device was waiting for redirected messages meant for that device to a third one (such an offer is now refused).
2. *The second review* (after the fixes of the first; it is the reason 1.0.106 was not published) found: (a) a device id containing a line break split the same signed bytes in two ways. With such an entry in the device list, a device hosting the hub re-bound one device's session to another device: a command sent to that entry was decrypted and executed by a different device, with the sender's rights. The hub could neither read nor alter the command. Measured in a test on both platforms, before and after the fix. (b) With an entry planted in the circle of trust and a hidden capability, a hub had answers to a device with an already proven key sent unprotected again. (c) One paired device could evict the sessions of others and pin more than a gigabyte of memory; a list of made-up devices triggered an unlimited number of signatures with the device key. (d) An unusual message from a hub ended the connection to it; on Android a very deeply nested message crashed the program.
3. *The third review* (only the fixes of the second) found no serious defect. It pointed out three improvements, all included: the per-device session limit of the first fix could push out a live session of another program of the same device (superseded sessions now go first); devices without a key in the circle no longer use up handshakes; a message that cannot be sent after a completed handshake is reported to the sender at once.
4. *The fourth review* (two separate reviewers, final state) confirmed the core of the protocol and found that a paired device with a modified program – or a hub – could overload another device: (a) every received offer triggered a signature with the device key, even the same offer repeated forever (measured: 500 offers = 500 signatures); (b) the program kept whole sent messages for acknowledgements, and an answer repeated an arbitrarily long command id – a device without any access could fill memory that way; the queues of pending handshakes had no byte limit; (c) the permissions file was written by several programs of the computer at the same time without a lock (measured: a failed write in 3 of 3 runs with two programs writing); (d) on Android, text that is not strict JSON hid nesting depth from the check. Hence the signature limit, short descriptors instead of messages, byte limits on queues and the locked permissions file (above).
5. *The fifth review* (two reviewers, the state after the fourth) found no defect that would stop the release. It pointed out hardening that is included: a repeating remote-control key aimed at a device that is currently not in the Link used up the signature limit and closed handshakes with it for a minute after it returned (now a short pause without a signature, and separate limits); the signature limit applied to a connection, not to the program; the mark "this device has proven its key" was not restored on disk after an older program of the same computer rewrote the permissions file without it; an unreadable permissions file gave inherited (full) rights instead of none; a rejected middle part of a long message looked "accepted" to the sender; a message id that is not a string bypassed the length limit; messages waiting for a handshake vanished without notice when the device was removed or the answer came too late.
6. *The sixth review* (two reviewers, only the changes after the fifth) again found no defect that would stop the release. It found one defect introduced by a fifth-round fix: a program that held the lock of the permissions file for too long could overwrite a change another program had made meanwhile – including a withdrawal of access (measured in a test; the file is now checked right before it is replaced and the change is applied again) – and five smaller ones: after a "no session" notice a later acknowledgement from the hub reported the same message again, possibly as "accepted"; the pause after a failed handshake applied to a connection, not to the program; the record of one part of a long message could be pushed out, so that a rejection of that part went unnoticed; tidying up waiting messages could hold up reading; an error while sending one waiting message took the others with it.

**Measured live on 7 October 2026** (a computer with Safeer Control 2.1.63 and two phones with Safeer OS 0.5.65 – the final code of this release; the other devices in the same Link were still on older versions):

- Commands from the computer to a phone and their answers (device information, the list of programs, a file search) travelled protected: a short command with its answer took 0.04–0.06 s (the first one on a new session 0.09 s), the list of programs 0.05–0.16 s.
- The phone received the list of folders the computer shares. That this command travelled protected follows from the rules (a sender does not send an unprotected command to a device that announces protection, and the computer does not accept one in the name of a device that has proven its key); it was not measured separately in this direction.
- A long message from the computer to the phone: 120 kB in 3 pieces (answered after 0.15 s) and 700 kB in 15 pieces (0.31 s). A message above the limit (1.2 MB) was not sent, and the sender got the error at once.
- After the program on the phone had been restarted (twice), commands succeeded as soon as the phone's receiver was visible in the Link again (about 4 s after the start): the first in 0.09–0.12 s, the following ones mostly in 0.04–0.06 s (single ones up to 0.15 s); 37 consecutive commands without an error each time. There was no "no session" error.
- No way back to unprotected: with the previous release of the program put back on the computer (2.1.61, without protection) the phone refused the same command three times with the message "The command did not arrive protected. Update Safeer on the device that sends it."; with this release the commands worked again.
- At first sight two devices proved their keys to each other without any command: 0.12 s after the second phone had connected to the Link with this release for the first time, it had recorded the proven keys of the computer and of the first phone, and they had recorded its key. Commands from the computer to it then travelled protected (0.05–0.16 s).
- Older devices in the same Link worked as before: a TV, a tablet and a Windows computer answered over the unprotected path.
- The phone's log showed no dropped messages during the measurement: the strict format checks rejected nothing in normal use; the only refusals were the three unprotected commands of the test above.

In addition to the code tests, the protection was put under load in memory before release (a tool outside the repository, both implementations): several threads send at the same time while the "hub" randomly rejects, delays or drops messages, delivers a message and "rejects" it at the same time, and forges "no session" notices, and the programs restart in between. In 30 runs of the computer implementation and 20 runs of the Android implementation (more than 300,000 sent messages in total) the receiver got every message at most once, the sender got at most one outcome for each – or "accepted" followed by "no session", but never the same outcome twice and never "accepted" after a rejection –, no thread stalled and nothing was left waiting in the queues.

**Not measured live** (covered by code tests only): a page or a stream that opens by itself, playback control and "continue on this device" over the protected path; a long message from a phone to the computer; a forged "no session" notice, a session id collision, a forged sender or a look-alike id in a real Link (checked by code tests; we do not inject these into a real Link); that a hub cannot read the messages (code tests; traffic was not captured); a hub that rejects or delays offers (code tests and the in-memory load run); several programs of the computer writing the permissions file at the same time (code tests); removing a device from the circle during a live session; Global Link; a TV and a tablet with this release; control of a shared screen.

Tests: the whole suite passes locally both ways it is run: 1174 tests with pytest (10 skipped) and 2016 tests with unittest, the way CI runs it (23 skipped). One test that starts a real hub on the machine cannot run on the development computer, where a hub is already running; it runs in CI, which has to pass before the release is tagged. New: `tests/test_link_e2e.py` (fixed test vectors shared with the Android implementation, the handshake, a hostile hub, look-alike ids, the connection of a program, the cases from all six reviews); `tests/test_link_dostop.py` extended (access by key, refusal of unprotected commands, storage keys, the form of ids, protection required by the form of an id, several programs writing the permissions file, an unreadable file); `tests/test_os_linux.py` extended (start at sign-in).

Not closed by this release:

- A device that has not been updated can still be impersonated towards other devices by whoever hosts a hub or presents its id – exactly as before this release. Update every device.
- Two updated devices are protected from the moment they have proven their keys to each other, which happens by itself when they first see each other. Until then a hub that is the only path between them could hide that they support protection and keep them on the unprotected path.
- The device list and the names in it are still written by the hub. It could show a made-up device under a familiar name; a command or a file you send to such a device is not protected. A "key verified" mark in the device list is the next step.
- Sync (bookmarks, open pages, positions in films – `sync.data`), a shared screen (`share.screen`) and playback state (`cast.status`) still travel as before: a hub sees them and could forge them – including the start of a screen share in the name of a device that has "Screen and control", which opens the address the message names. Protecting these messages is the next step.
- Sharing a phone's internet connection (Safeer Internet Gateway, `internet.*`) still recognises a device by the id the hub writes; the device key does not decide there yet.
- What you send explicitly (text, a file, a chat message) is forwarded and seen by the hub as before.
- Content itself (files, video and audio streams, the picture of a screen) travels over its own connections as before; this release does not change them.
- The receiver's acknowledgement of a protected page or playback control ("accepted" or "not allowed") still reaches the hub unprotected: it sees the message id and the outcome, not the content.
- A hub can still drop a message – or hold it and deliver it later while the session lasts (at most 12 hours); the command then runs late.
- The signature limits bound the damage, they do not prevent it: with forged "no session" notices a hub can use up the handshake limit for one device. Commands to that device then fail while the hub keeps doing it and for up to one minute afterwards. It can neither read nor forge them.
- Signing in to a hub signs a challenge in which the hub itself names its fingerprint: a malicious hub can relay the challenge of another hub and sign in there as this device. This affects only messages that are not protected yet (see above); protected commands can be neither read nor sent that way.
- The computer sends a protected message while holding the lock of the protection code: a hub that stops reading holds up the other protected commands of that program until the connection is dropped.
- A command sent at the very moment the program on the other device restarts can fail; it is not repeated automatically (see "Every command is sent exactly once").
- Any member of the Link can still remove or rename a device, and sees the pairing code of a new device. Legacy device ids (not derived from a key) are bound only by their entry in the circle of trust: whoever may change the circle can replace such an entry. Per-device limits are per key: a member who adds several keys to the circle gets that many limits. The circle of trust still stores an entry "id derived from a key, with a different key" (such an entry has no access – see above).
- The narrower circle is still set on each device separately.
- The device id derived from a key is 64 bits of the key's hash; a longer one is planned, together with length-prefixed handshake fields.
- Safeer Control for Windows and Safeer Browser for Android (the mobile browser) do not have protection yet.

## Safeer OS 0.4.65

- **Safeer OS starts at sign-in only if you switch that on.** Until now Safeer OS switched on "Start when I sign in" by itself the first time it was opened. From this release it does not: it starts at sign-in only when you switch it on in Settings → "Start when I sign in". Where an earlier version had switched it on by itself, this update switches it off once; if you want it, switch it on again and it stays on. The Safeer OS desktop theme for Linux Mint (the separate package `safeer-os-tema`, which you install to make Safeer OS your desktop) is not affected.
- Safeer Link inside Safeer OS uses the same protection as Safeer Control 2.1.63.

## Safeer Browser 1.0.107

- Released together with Safeer Control 2.1.63. Safeer Link inside the browser uses the same protection. No other changes.

Slovensko: **Varnost: ukazi med napravami so podpisani s ključem naprave in šifrirani od naprave do naprave.** Izdaja 1.0.105 je uvedla, da vsaka naprava sama odloča, kaj ji druga naprava sme. Ta odločitev pa je še vedno slonela na oznaki naprave, ki jo v posredovano sporočilo vpiše središče. Izmerjeno 7. 10. 2026 v krajevnem preizkusu: oznaka, ki je le podobna oznaki druge naprave, je dobila njen dostop. Iz zgradbe pa sledi: središče ta sporočila posreduje nešifrirana in pošiljatelja vpiše samo, zato bi jih, kdor središče gosti, lahko bral in vanje vpisal kateregakoli pošiljatelja. Različice 1.0.106 / Safeer Control 2.1.62 / Safeer OS 0.4.64 so bile pripravljene, a niso bile objavljene: drugi neodvisni pregled je pred objavo našel napake, ki jih ta izdaja odpravlja. Zdaj si napravi pred ukazom dokažeta ključ: vsaka podpiše svoj del dogovora s ključem naprave, druga ga preveri s ključem iz svojega kroga zaupanja; sporočila so šifrirana (AES-256-GCM), ključ seje nastane iz enkratne izmenjave ECDH. Zaščiteno gredo ukazi, odgovori nanje, stran ali pretok, ki se odpre sam, nadzor predvajanja in »nadaljuj na napravi«; naslov, prstni odtis in žeton strežnika datotek pridejo v zaščitenem odgovoru. O dostopu odloča ključ, ne oznaka. Ko naprava ključ enkrat dokaže, računalnik v njenem imenu ne sprejme več nezaščitenega ukaza – od nikogar – in ji odgovarja samo zaščiteno; tega ne ugasne ne podtaknjen vnos v krogu ne središče, ki zmožnost naprave zamolči. Odgovor na zaščiten ukaz velja samo iz seje naprave, ki smo jo vprašali. Vsak ukaz se pošlje natanko enkrat (po obvestilu »seje ni« se ne ponovi – obvestilo ni podpisano). Odstranitev naprave iz kroga velja takoj. Oznake in polja dogovora imajo strogo obliko, preverjeno pred podpisom in preverbo; ena naprava ne more izriniti sej drugih ali zasesti pomnilnika. Starejše naprave delajo kot prej, dokler jih ne posodobiš – in so zaščitene le toliko kot prej. Zaščita deluje, ko imata obe napravi to izdajo (računalnik: Safeer Control 2.1.63; Android: Safeer OS 0.5.65); vse programe Safeer na eni napravi posodobi skupaj. Šest pregledov pred izdajo (notranji, ločeni od razvoja; niso zunanja revizija; popravki po šestem niso bili pregledani še sedmič – preverjeni so s preizkusi, ki so prej padli, in z meritvijo prej/potem): prvi je našel ponovitev izvedenega ukaza po ponarejenem obvestilu in trk oznake seje; drugi, da je oznaka naprave s prelomom vrstice sejo ene naprave prevezala na drugo (ukaz se je izvedel na drugi napravi; vsebine središče ni videlo), da je podtaknjen vnos v krog znova odprl nezaščitene odgovore, da je ena naprava lahko izrinila seje drugih, in da je nenavadno sporočilo prekinilo povezavo; tretji v popravkih ni našel resne napake; četrti je potrdil jedro protokola in našel, da seznanjena naprava s predelanim programom ali središče drugo napravo lahko preobremeni (neomejeno podpisov s ključem naprave, cela sporočila v pomnilniku, zapis dovoljenj brez zaklepa med programi) – zato meja 32 podpisov na napravo na minuto v vsako smer, kratki opisi namesto sporočil, meje vrst in zaklenjen zapis dovoljenj; peti in šesti nista našla napake, ki bi izdajo ustavila, le utrditve, ki so vključene – med njimi napako, ki jo je uvedel popravek po petem pregledu (program, ki je predolgo držal zaklep zapisa dovoljenj, je lahko povozil spremembo drugega programa, tudi odvzem dostopa). Vse najdbe so bile najprej pokazane s preizkusom, ki je padel, in popravljene pred izdajo. **Safeer OS 0.4.65:** ob prijavi v računalnik se zažene samo, če to vklopiš v Nastavitvah (»Zaženi ob prijavi v računalnik«); kjer si ga je starejša različica vklopila sama, ga ta posodobitev enkrat izklopi.
