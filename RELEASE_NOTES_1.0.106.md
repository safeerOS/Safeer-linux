# Safeer Browser for Linux 1.0.106 · Safeer Control 2.1.62 · Safeer OS 0.4.64

## Security: commands between devices are signed with the device key and encrypted from device to device (Safeer Control 2.1.62)

Release 1.0.105 made every device decide for itself what each other device may reach on it. That decision, however, still rested on the device id which the hub writes into a message it routes. Measured on 7 October 2026 in a local test: an id that merely looks like the id of another device was given that device's access. And by construction a hub routes these messages unencrypted and writes the sender into them itself, so whoever hosts a hub could read the commands and answers it routes (file lists, what is playing, addresses and tokens of the file server) and name any sender.

From this release two devices prove their keys to each other, and the device that holds the content decides by the key:

- **A protected session between two programs.** Each side signs its part of the handshake with the device key – the key that is already in your circle of trust – and the other side verifies it with the key from *its own* copy of the circle. The session key comes from a one-time ECDH exchange (P-256), so the device key only ever signs. Messages are encrypted with AES-256-GCM, each direction with its own key and a strictly increasing counter.
- **What travels protected:** commands (`control.command`), their answers (`control.result`), a page or a stream that opens by itself (`cast.url`), playback control (`cast.control`) and "continue on this device" (`handoff.request`). The hub forwards a signed handshake and encrypted pieces; it sees neither the command nor the answer. The address, the certificate fingerprint and the token of the file server arrive inside the protected answer.
- **Access is decided by the key.** For a protected message the computer looks up access by the id derived from the *verified key*, not by the id written into the message.
- **No way back to unprotected.** Once a device has proven its key to this computer, the computer no longer accepts these messages unprotected in that device's name – from anyone. A program sets up protection with a device that announces it as soon as it appears in the device list, not only at the first command – also after its own restart, when it no longer has the old sessions.
- **An answer must come from the device that was asked.** An answer to a protected command is accepted only from the verified session of that device.
- **Every command is sent exactly once.** If the other device no longer knows the session, the command is not sent again: the "no session" notice is unsigned, so a hub could send it too and have an already executed command repeated. The sender is told at once; the next command uses a new session.
- **Removing a device takes effect immediately.** A session is valid only while the device key is in your circle of trust.
- **An id that carries another device's name gets nothing.** An id derived from a key (`n-…`) under which the circle of trust holds a *different* key has no access at all – on the unprotected path too – and shares nothing that was stored for the real device.
- **Only the agreed message types travel protected.** A paired device cannot use the protected path to send what otherwise only a hub sends (the device list, the circle of trust, a pairing code).
- **Older devices keep working as before** until they are updated – and are only as protected as before. When a program without protection sends a command in the name of a device that has it, it receives the answer "The command did not arrive protected. Update Safeer on the device that sends it."

Both devices need this release for protection: Safeer Control 2.1.62 / Safeer Browser 1.0.106 on a computer, Safeer OS 0.5.64 on a TV, tablet or phone. Update all Safeer programs on one device together – they share the device key, and once one of them has proven it, updated devices refuse commands from an older program of the same device.

**Pre-release review.** Before release the protection code was reviewed once more, separately from development (an internal review; not an external security audit). It found two defects; each was first reproduced with a failing test and fixed before release: (1) with a forged "no session" notice a hub made an already executed command run again – four times after three notices in the test (which is why commands are no longer re-sent); (2) an offer from another device that reused the session id of a handshake this device was waiting for redirected messages meant for that device to a third one (such an offer is now refused). The same review led to several hardenings: a session does not survive the removal of a device, stale queued messages are not sent, replayed old offers cannot push out a working session, and no message can end the connection to the hub.

**Measured live on 7 October 2026** (a computer with Safeer Control 2.1.62 and a test phone with Safeer OS 0.5.64 – the final code of this release; the other devices in the same Link were still on older versions):

- Commands from the computer to the phone and their answers (device information, the list of programs) travelled protected: a short command with its answer took 0.03–0.05 s, the list of programs up to 0.13 s.
- The phone received the list of folders the computer shares. That this command travelled protected follows from the rules (a sender does not send an unprotected command to a device that announces protection, and the computer does not accept one in the name of a device that has proven its key); it was not measured separately in this direction.
- A long message from the computer to the phone: 120 kB in 3 pieces (answered after 0.13 s) and 700 kB in 15 pieces (0.33 s). A message above the limit (1.2 MB) was not sent by the sender.
- After the program on the phone had been restarted (four times), commands succeeded as soon as the phone's receiver was visible in the Link again (about 4 s after the start): the first in 0.08–0.10 s, the following ones mostly in 0.03–0.05 s. There was no "no session" error.
- Older devices in the same Link worked as before: a TV, a tablet, another phone and a Windows computer answered over the unprotected path; a device with 0.5.63 that has not opened access to the computer refused the command as before.
- With the previous release of the program put back on the computer (2.1.61, without protection) the phone refused the same commands with the message quoted above, and with this release they worked again (measured with an earlier test build of this code; the review fixes did not change this path).
- At first sight the two devices proved their keys to each other without any command, and both recorded it (measured with an earlier test build of this code; in the final measurement the devices were already recorded).

**Not measured live** (covered by code tests only): a page or a stream that opens by itself, playback control and "continue on this device" over the protected path; a long message from a phone to the computer; a forged "no session" notice, a session id collision, a forged sender or a look-alike id in a real Link (checked by code tests; we do not inject these into a real Link); that a hub cannot read the messages (code tests; traffic was not captured); removing a device from the circle during a live session; Global Link; a TV, a tablet and other phones with this release; control of a shared screen.

Tests: the whole suite passes locally both ways it is run: 1098 tests with pytest (10 skipped) and 1936 tests with unittest, the way CI runs it (23 skipped). One test that starts a real hub on the machine cannot run on the development computer, where a hub is already running; it runs in CI and passed there. New: `tests/test_link_e2e.py` (fixed test vectors shared with the Android implementation, the handshake, a hostile hub, look-alike ids, the connection of a program, the cases from the review); `tests/test_link_dostop.py` extended (access by key, refusal of unprotected commands, storage keys).

Not closed by this release:

- A device that has not been updated can still be impersonated towards other devices by whoever hosts a hub or presents its id – exactly as before this release. Update every device.
- Two updated devices are protected from the moment they have proven their keys to each other, which happens by itself when they first see each other. Until then a hub that is the only path between them could hide that they support protection and keep them on the unprotected path.
- The device list and the names in it are still written by the hub. It could show a made-up device under a familiar name; a command or a file you send to such a device is not protected. A "key verified" mark in the device list is the next step.
- Sync (bookmarks, open pages, positions in films – `sync.data`), a shared screen (`share.screen`) and playback state (`cast.status`) still travel as before: a hub sees them and could forge them – including the start of a screen share in the name of a device that has "Screen and control", which opens the address the message names. Protecting these messages is the next step.
- What you send explicitly (text, a file, a chat message) is forwarded and seen by the hub as before.
- Content itself (files, video and audio streams, the picture of a screen) travels over its own connections as before; this release does not change them.
- A hub can still drop a message – or hold it and deliver it later while the session lasts (at most 12 hours); the command then runs late.
- A command sent at the very moment the program on the other device restarts can fail; it is not repeated automatically (see "Every command is sent exactly once").
- Any member of the Link can still remove or rename a device, and sees the pairing code of a new device.
- The narrower circle is still set on each device separately.
- The device id derived from a key is 64 bits of the key's hash; a longer one is planned.
- Safeer Control for Windows and Safeer Browser for Android (the mobile browser) do not have protection yet.

## Safeer OS 0.4.64 · Safeer Browser 1.0.106

- Released together with Safeer Control 2.1.62. Safeer Link inside the browser uses the same protection. No other changes.

Slovensko: **Varnost: ukazi med napravami so podpisani s ključem naprave in šifrirani od naprave do naprave.** Izdaja 1.0.105 je uvedla, da vsaka naprava sama odloča, kaj ji druga naprava sme. Ta odločitev pa je še vedno slonela na oznaki naprave, ki jo v posredovano sporočilo vpiše središče. Izmerjeno 7. 10. 2026 v krajevnem preizkusu: oznaka, ki je le podobna oznaki druge naprave, je dobila njen dostop. Iz zgradbe pa sledi: središče ta sporočila posreduje nešifrirana in pošiljatelja vpiše samo, zato bi jih, kdor središče gosti, lahko bral in vanje vpisal kateregakoli pošiljatelja. Zdaj si napravi pred ukazom dokažeta ključ: vsaka podpiše svoj del dogovora s ključem naprave, druga ga preveri s ključem iz svojega kroga zaupanja; sporočila so šifrirana (AES-256-GCM), ključ seje nastane iz enkratne izmenjave ECDH. Zaščiteno gredo ukazi, odgovori nanje, stran ali pretok, ki se odpre sam, nadzor predvajanja in »nadaljuj na napravi«; naslov, prstni odtis in žeton strežnika datotek pridejo v zaščitenem odgovoru. O dostopu odloča ključ, ne oznaka. Ko naprava ključ enkrat dokaže, računalnik v njenem imenu ne sprejme več nezaščitenega ukaza – od nikogar. Odgovor na zaščiten ukaz velja samo iz seje naprave, ki smo jo vprašali. Vsak ukaz se pošlje natanko enkrat (po obvestilu »seje ni« se ne ponovi – obvestilo ni podpisano). Odstranitev naprave iz kroga velja takoj. Starejše naprave delajo kot prej, dokler jih ne posodobiš – in so zaščitene le toliko kot prej. Zaščita deluje, ko imata obe napravi to izdajo (računalnik: Safeer Control 2.1.62; Android: Safeer OS 0.5.64); vse programe Safeer na eni napravi posodobi skupaj. Pregled pred izdajo (notranji, ločen od razvoja; ni zunanja revizija) je našel dve napaki, obe pokazani s preizkusom, ki je padel, in popravljeni pred izdajo. Kaj ostaja odprto, je našteto zgoraj (»Not closed by this release«).
